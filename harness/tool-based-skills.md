# Tool-based skills

A skill encodes judgment: when to act, why, and how to use the tools beneath it. A tool encodes
procedure: the schema a document must satisfy, the check a change must pass, the transformation a
step performs. A skill that carries its own procedure in prose is brittle, consumes context on
every load, and drifts from what runs; a tool that carries it is testable, versioned, and
identical every time it is invoked. So a skill of any complexity is accompanied by tooling that
handles its procedural details, and the skill's text describes the logical behavior that trains
the agent to use that tooling. A specification of functionality is never encoded in a skill when
traditional tooling would fit it better.

## What a tool carries and what a skill carries

- A tool carries the checks: a `lint`, a `schema`, or a `validate` command in place of an
  instruction such as "the front matter must contain a key." A tool that reconciles an authored
  document against an external system exposes a `plan` command that shows the difference and
  an `apply` command that performs it, and records what it applied.
- A skill says "run the tool and resolve its findings" and does not restate what the tool
  checks. It decides when the tool runs, what a finding means, and what to do next.
- A skill that grows a procedural section has found a candidate tool.

## The three layers a tooling domain is built in

A domain that serves an agent is layered as specification, tooling, and skill, bottom to top,
each depending only on the layer below it. The specification scopes the domain: its document
formats and their schemas. The tooling makes the specification operable: the commands that
validate, scaffold, and transform. The skill decides when and why to act. Keeping the layers
distinct lets each be replaced or consumed on its own: a program that is not an agent uses the
tooling, a different agent uses the specification, and the specification and the tooling are
testable with no agent present. A domain is a specification and its tools, which a skill may
sit thinly on top of; it is never "a skill."

## Where the schema is the contract

Any output of a skill that external tooling consumes has a formal schema, written in a
language-neutral form such as JSON Schema. The schema is the contract: code validates against
it and never defines it, so a command-line tool, a plugin, a web application, an extension, or
another agent validates the same document against the same file without importing any
implementation. Schemas live in a versioned `spec/` directory, one per document type; a type
in the host language is derived from the schema or validated against it and is never the only
definition; and a schema change is versioned and reviewed the way an API change is. The
[schema-driven skill artifacts](schema-driven-artifacts.md) principle states where those
documents live; this principle states what governs their shape.

## How a specification and an instance separate

Anything a domain scaffolds for others is split into a specification repository, holding the
schemas, the tooling, the adapters, and the documentation, and an instance repository, holding
one person's or one team's actual data, generated by the tooling and pinned to a version of the
specification. Copying a personal repository as a starting point leaks personal data and
couples every consumer to one author's state. A scaffold produces a clean instance, an
initialization command never copies an existing instance's entries, and an instance records the
specification version it targets so an upgrade is a deliberate bump.

## How an extension uses the tooling

A workflow extension invokes the tooling's commands and never re-encodes their process: the
lint runs before a commit, the plan is surfaced for review, the apply is a step. If the
extension needs behavior the tooling lacks, the tooling gains a command. One process lives in
one place, and an extension that reimplements a check is a second source of truth that drifts.

## When work is offloaded to another model

Work moves from the agent to a local or specialized model when it is structured, repetitive,
and schema-validated, never because the agent is assumed weak at it. The gains are cost,
locality, and determinism for a fixed transformation; quality-sensitive generation stays with
the stronger model. The offload is itself a tool: a fixed prompt template, an endpoint, and
output validated against the schema before it is used, so the agent orchestrates and never
handles the generated content. Rollups, reformatting to a template, and drafts from a fixed
structure are the candidates.

## How much custom code a domain carries

Custom code is limited to scaffolding, validation, and schema enforcement. Everything else is
configuration, an adapter, or documentation, because code that exists to express process is
the code that rots. Before a command is added, it is one of scaffold, lint, schema, plan,
apply, or export; if it is none of those, it is an adapter or a document.

## How a domain is built first

The first slice is one document type, one provider, and the full command loop, and everything
else is designed against that loop rather than ahead of it. Long-term features recorded up
front, such as a user interface or a collaboration layer, are constraints the design respects,
not work it starts; a working loop is what exposes which abstractions are real.

## Worked examples

The marathon-roadmap extension keeps its manifest in one schema-stable file,
[`context/roadmap.toml`](https://github.com/standards-lab/claude-plugins/blob/main/plugins/marathon-roadmap/skills/marathon-roadmap/references/manifest.md),
whose format the skill documents in prose; the validator over that format is the tool this
principle asks for, and the skill's hook instructions are the judgment that would call it. The
[sqlate library](https://github.com/standards-lab/sqlate)'s conventions linter is the shape of
such a tool: the conventions are checked by a package a command wraps, and a skill that
enforces them calls the command rather than restating the checks.
